# LandGuard AI

**Predict delays before infrastructure land-acquisition projects get stuck.**

A full-stack predictive analytics system for SIH26017 ("Predictive Analytics System for Early
Detection of Land Acquisition Delays"). Officials get an AI-generated risk score for every
project, a plain-English explanation of *why* it's at risk, a heatmap of hotspots across India,
early-warning alerts, a 30/60/90-day forecast, a what-if simulator, department-level bottleneck
detection, and a natural-language assistant (LandBot AI) — all ten features from the original
concept brief.

The backend runs on the **originally-proposed stack**: FastAPI, PostgreSQL via SQLAlchemy,
XGBoost, SHAP, and python-jose + passlib/bcrypt for auth. It's structured to deploy straight to
Vercel (see "Deploying to Vercel" below) alongside the React/Vite frontend.

---

## What's implemented (all 10 features from the original brief)

1. **AI Risk Score** — a trained XGBoost classifier predicts probability of delay (0-100%) for every project.
2. **Explainable AI** — SHAP-based top risk factors with % contribution and direction, e.g. "Compensation NOT yet disbursed: 62% (increases risk)".
3. **India Risk Heatmap** — an interactive Leaflet map of all projects color-coded by risk tier, plus a district-level summary table.
4. **Early Warning Alerts** — fired automatically whenever a re-scored project's risk tier worsens (e.g. Medium → High), naming the leading cause and a suggested action.
5. **Risk Timeline Forecasting** — projects risk 30/60/90 days out if nothing changes.
6. **What-If Simulator** — toggle "resolve legal disputes" / "release compensation" / "clear approvals" and see the predicted risk score change live.
7. **Coordination Bottleneck Detection** — aggregates pending approvals by department to show which one (Revenue, Legal, Forest, Finance, ...) is the actual bottleneck, globally or per-project.
8. **Admin Dashboard** — total projects, risk tier breakdown, critical alerts, compensation pending, active legal cases.
9. **LandBot AI** — answers natural-language questions about the app's live data. By default it's a rule/retrieval-based assistant (no external API key required) recognizing a broad set of intents. Optionally, set a free `GROQ_API_KEY` (see "Upgrading LandBot AI to a real LLM" below) to swap in a real hosted LLM (`openai/gpt-oss-120b` by default) that uses function-calling against the database, so it can answer genuinely arbitrary phrasings instead of only recognized intents — and it automatically falls back to the offline bot if the key is missing or a request fails.
10. **Recommendation Engine** — every risk assessment comes with prescriptive, ranked actions (not just a score).

All data is **synthetic** (260 realistic Indian land-acquisition projects across 12 states/45
districts, generated by `app/ml/data_generator.py`) — no real government data was used or is
required.

## Running it locally

### Backend

Requires Python 3.10+ and a PostgreSQL database (see "Getting a database" below if you don't
have one yet — a free Neon database takes about two minutes to set up and works the same
whether you're running locally or on Vercel).

```bash
cd backend
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
python -m pip install -r requirements.txt
```

Then create `.env` in `backend/` from the example file (this is a plain copy, but the command
differs by shell):

```bash
cp .env.example .env             # macOS/Linux, or Windows PowerShell (cp is aliased there)
copy .env.example .env           # Windows Command Prompt (cmd.exe) — cp isn't a real command there
```

Paste your `DATABASE_URL` (and ideally `DATABASE_URL_UNPOOLED`) into the new `.env` — see
"Getting a database" below. Then:

```bash
python -m app.ml.train           # trains the XGBoost risk models (~10-30s), saves to app/ml/artifacts/
python -m app.seed                # (re)creates all tables and seeds 260 projects + initial risk scores

python -m uvicorn app.main:app --reload --port 8000    # starts the API on http://localhost:8000
```

`python -m pip` / `python -m uvicorn` (rather than a bare `pip` / `uvicorn` command) make sure
the package gets installed into, and later run from, the *same* Python interpreter — on Windows
especially, a bare `pip`/`uvicorn` command can silently resolve to a different Python install
than the one `python` points to, which looks like "I installed it, but it says the module is
missing."

If you leave `DATABASE_URL` blank in `.env`, the app falls back to a local SQLite file
(`backend/landguard.db`) purely so it boots for a quick look with zero setup — this is **not** a
supported path for anything beyond that; `python -m app.seed` and the rest of this README assume
Postgres.

Demo logins: `admin` / `admin123` (role: admin) or `official` / `official123`.

Quick smoke test:

```bash
curl -X POST http://localhost:8000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123"}'
```

Interactive API docs (FastAPI auto-generates these): `http://localhost:8000/docs`.

For a non-Vercel production deployment on Linux/macOS, run behind gunicorn's uvicorn worker
instead of `--reload`: `gunicorn -w 4 -k uvicorn.workers.UvicornWorker app.main:app` (from
`backend/`). Gunicorn doesn't run on Windows (it relies on `fork()`), so this line only applies
if you're deploying to a Linux/Mac host yourself — it's irrelevant for local Windows dev or for
the Vercel path above, both of which use uvicorn directly.

### Frontend

Requires Node.js 18+.

```bash
cd frontend
npm install
```

Then create `.env` from the example file the same way as above (`cp .env.example .env` on
macOS/Linux/PowerShell, `copy .env.example .env` on Windows cmd.exe) — it just points
`VITE_API_BASE_URL` at your backend. Then:

```bash
npm run dev                     # http://localhost:5173
```

## Getting a database

The app needs a PostgreSQL connection string in `DATABASE_URL` (and, ideally,
`DATABASE_URL_UNPOOLED` — see below). Any Postgres works, but the easiest free option, and the
one that plugs straight into the Vercel deployment path below, is
[Neon](https://neon.tech):

1. Create a free Neon project at [console.neon.tech](https://console.neon.tech) (or install Neon
   from the **Vercel Marketplace** directly against your Vercel project — see "Deploying to
   Vercel" below, which does this same step for you and injects the env vars automatically).
2. From the Neon console, copy the **pooled** connection string into `DATABASE_URL` and the
   **direct/unpooled** one into `DATABASE_URL_UNPOOLED` in `backend/.env`.
3. Run `python -m app.ml.train` then `python -m app.seed` as above — `seed.py` always uses the
   unpooled connection (schema drop/create and a few thousand inserts behave better outside a
   transaction-mode pooler than a normal request does).

> **A note on "Vercel Postgres":** Vercel used to sell first-party Postgres under that name.
> It was migrated to Neon in December 2024 and is no longer offered as a separate product — if
> you don't see a literal "Vercel Postgres" option in your dashboard, that's why. The
> Neon-via-Marketplace path above (and in the Vercel deployment steps below) is the current
> equivalent, and it's what this app's env var names (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`)
> already match.

## Deploying to Vercel

This deploys as **two separate Vercel projects** from the same repo: one for `backend/`, one for
`frontend/`.

### 1. Backend project

1. In Vercel, "Add New Project" → import this repo → set **Root Directory** to `backend`.
   Vercel's Python runtime auto-detects the FastAPI `app` instance in `app/main.py` — no build
   command or entrypoint config needed for that part.
2. Before or after the first deploy, add the **Neon Postgres** integration from the **Vercel
   Marketplace** (Project → Storage → Browse Marketplace → Neon) and connect it to this project.
   This injects `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, and a few other Postgres env vars
   automatically — no copy-pasting connection strings.
3. Add the remaining environment variables under Project → Settings → Environment Variables:
   - `SECRET_KEY` — any long random string (used to sign JWTs).
   - `CORS_ORIGINS` — the frontend project's URL once you know it (step 2 of the frontend
     section below), comma-separated if you need more than one (e.g. a custom domain too).
   - `GROQ_API_KEY` / `GROQ_MODEL` / `LLM_CHATBOT_ENABLED` — optional, only if you want the real-LLM
     chatbot upgrade (see below).
4. Seed the remote database once, from your own machine (Vercel Functions aren't a great fit for
   running a one-off admin script):
   ```bash
   cd backend
   npx vercel link              # links this folder to the Vercel project you just created
   npx vercel env pull .env.local
   # copy DATABASE_URL / DATABASE_URL_UNPOOLED from .env.local into your backend/.env
   python -m app.ml.train
   python -m app.seed
   ```
5. Deploy (`npx vercel --prod`, or just push to the branch Vercel is tracking).
6. If chatbot calls or ML inference need more than the default execution window, adjust
   `maxDuration` in `backend/vercel.json` — the ceiling depends on your Vercel plan, so check
   your dashboard's limits if you raise it and it's rejected.

The trained model artifacts under `app/ml/artifacts/` are committed to the repo (from step 4) and
deployed as-is — Vercel doesn't retrain them on every deploy. Re-run `python -m app.ml.train` and
commit the updated artifacts whenever you want to retrain.

### 2. Frontend project

1. "Add New Project" → import the same repo again → set **Root Directory** to `frontend`.
   Vite is zero-config on Vercel (build command `npm run build`, output `dist`).
2. Add one environment variable: `VITE_API_BASE_URL` = your backend project's URL (from step 1
   above), e.g. `https://landguard-backend.vercel.app`.
3. Deploy. `frontend/vercel.json` adds the SPA rewrite rule client-side routing needs (without
   it, refreshing a deep link like `/projects/12` would 404).
4. Go back to the backend project's `CORS_ORIGINS` env var and make sure it includes this
   frontend URL, then redeploy the backend if you changed it after step 1.

## API reference (all under `/api`, all except `/auth/login` and `/health` require
`Authorization: Bearer <token>`)

| Method & path | Purpose |
|---|---|
| `POST /api/auth/login` | Get a JWT access token |
| `GET /api/auth/me` | Current user |
| `GET /api/projects` | List projects (filters: `state`, `district`, `project_type`, `risk_tier`, `search`) |
| `GET /api/projects/meta/filters` | Distinct states/districts/types for filter dropdowns |
| `GET /api/projects/<id>` | Full project detail incl. approvals + disputes |
| `GET /api/projects/<id>/risk` | Latest risk assessment (computes one if none exists) |
| `POST /api/projects/<id>/recompute` | Force-recompute risk (fires an alert if the tier worsened) |
| `POST /api/projects/<id>/simulate` | What-if simulation — body: `{resolve_legal_disputes, release_compensation, complete_pending_approvals, reduce_approval_days_to}` |
| `GET /api/alerts` | List alerts (filters: `severity`, `acknowledged`, `limit`) |
| `POST /api/alerts/<id>/acknowledge` | Mark an alert acknowledged |
| `GET /api/heatmap/districts` | District-level risk aggregates (for the map + table) |
| `GET /api/dashboard/summary` | Aggregate dashboard stats |
| `GET /api/bottleneck` | Global department bottleneck report |
| `GET /api/bottleneck/project/<id>` | Per-project bottleneck report |
| `POST /api/chatbot` | LandBot AI — body: `{"message": "..."}` |

## Upgrading LandBot AI to a real LLM (optional)

Out of the box, LandBot AI (`app/chatbot.py`) is a rule/retrieval-based
assistant: it pattern-matches your message into one of a fixed set of
intents (top-N at risk, why-delayed, compensation, legal disputes,
bottlenecks, a specific project, a location catch-all, etc.), runs the
matching database query, and formats a sentence. It needs no API key and
works fully offline, but it can only answer question *shapes* it was
specifically coded to recognize.

Setting a free `GROQ_API_KEY` swaps in `app/llm_chatbot.py` instead: a real
hosted LLM (`openai/gpt-oss-120b` by default, via
[Groq](https://console.groq.com)'s free/low-cost OpenAI-compatible API) that
uses **function-calling** — it's given tools like `search_projects`,
`get_project_detail`, `get_compensation_summary`, `get_legal_disputes_summary`,
`get_bottleneck_report`, `get_dashboard_summary`, `get_alerts`, and
`list_known_filters`, decides which one(s) to call and with what arguments
based on your actual message, executes them against the real Postgres
database, and writes the final answer grounded in that real data. This means
it can answer genuinely arbitrary combinations ("high risk projects in
Chennai", "which state has the most legal disputes", "how much compensation
is still owed in Bihar") rather than only the hand-coded intents above.

**Setup** (no new pip packages needed — the HTTP call uses only the Python
standard library):

1. Get a free API key at [console.groq.com/keys](https://console.groq.com/keys).
2. Copy `backend/.env.example` to `backend/.env` and paste your key into
   `GROQ_API_KEY=` (locally), or add it as an environment variable on the
   backend Vercel project (see "Deploying to Vercel" above).
3. Restart the backend. Every `/api/chatbot` response now includes
   `"engine": "llm"` when the real model answered, or `"engine": "rule_based"`
   when it fell back (no key configured, or the API call failed for any
   reason — offline, bad key, rate-limited, timed out). The chat widget
   itself behaves identically either way.
4. To use a different Groq-hosted model (e.g. a Qwen model, or the smaller/
   faster `openai/gpt-oss-20b`), set `GROQ_MODEL` in `.env` — check
   [console.groq.com/docs/models](https://console.groq.com/docs/models) for
   current model ids, since availability changes.

This upgrade only touches LandBot AI — it doesn't change the risk-scoring
ML pipeline, which is unrelated.

## Notes on the ML approach

- **Synthetic data, not real government data.** `app/ml/data_generator.py` samples realistic
  Indian states/districts/project types and a *ground-truth* risk formula (compensation
  disbursement %, active legal disputes, ownership complexity, department count, district
  history, approval delay) with noise, then trains a classifier to recover that signal from the
  observable features — exactly the setup the classifier would face with real historical case
  data.
- **Risk tiers**: Low < 40% < Medium < 70% < High (configurable in `app/config.py`).
- **Explainability** (`app/ml/model.py`): SHAP's `TreeExplainer` against the trained XGBoost
  classifier gives true Shapley-value attributions for every prediction — how much each feature
  pushed the risk score up or down, which feeds directly into the recommendation engine and the
  What-If Simulator.
- **Forecasting**: risk at +30/60/90 days is computed by advancing the "longest-pending approval"
  clock forward and re-scoring, i.e. "if this approval keeps sitting unresolved."
